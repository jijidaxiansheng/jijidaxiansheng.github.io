STM32 烧录与构建链路复盘：从预处理到 ELF、HEX、BIN，再到代码烧进 Flash

发表于2026-05-07|编程基础
|浏览量:

STM32 相关的问题，一旦从“写代码”继续往下问，就很容易走到一条完整链路上：

  • 代码是怎么变成固件文件的？
  • hex 和 bin 有什么区别？
  • 烧录器到底是怎么把程序写进芯片的？
  • 预处理阶段到底做了什么？

这些问题表面上分属编译原理和硬件下载两个方向，但如果把流程串起来，其实就是一条从源代码走到 Flash 的完整路径。

一、先把整条链路压缩成一行

如果只用一行概括，STM32 工程从源码到芯片，大致经历的是：

源代码 -> 预处理 -> 编译 -> 汇编 -> 链接 -> ELF/AXF -> HEX/BIN -> 烧录到 Flash -> 复位运行

这条链里，前半段是工具链在处理“代码怎么变成机器指令”，后半段是在处理“这些机器指令怎么被写进目标芯片”。

二、预处理阶段到底在做什么

很多人知道预处理是第一步，但容易把它想得很“高级”。实际上，预处理器做的大多是文本层面的展开和裁剪。

4. 删除注释并插入行号信息

预处理器还会清掉注释，并保留必要的文件名和行号映射，方便后续编译报错时还能定位回原始源文件。

预处理的产物是什么

通常可以把它理解成一个展开后的中间文件，比如 .i 文件。这个文件里：

  • 头文件都已经展开了
  • 宏都已经替换了
  • 条件编译已经做完了
  • 注释已经去掉了

也就是说，到了这一步，代码已经更接近“纯 C 源文件”了。

三、编译、汇编、链接，三者别混

预处理之后，才真正进入大家熟悉的“编译链”。

1. 编译：把 C 代码变成汇编

编译器会把 C 语言逻辑翻译成目标架构的汇编指令。到了这一步，变量、表达式、函数调用、控制流，都会被翻译成更底层的表示。

2. 汇编：把汇编变成机器码

汇编器再把汇编指令翻译成二进制机器指令，生成目标文件，比如 .o 或 .obj。

这时候每个源文件通常都只变成了各自独立的一块机器码，还没真正拼成完整固件。

3. 链接：把零散目标文件拼成完整程序

链接器负责把：

  • 各个 .o 文件
  • 启动文件
  • 标准库
  • 第三方库

组合成一个完整可执行镜像。

更关键的是，链接器会根据链接脚本决定：

  • 哪些代码段放 Flash
  • 哪些数据段放 SRAM
  • 启动栈放哪里
  • 中断向量表放哪里

这也是为什么链接脚本在嵌入式里非常重要。因为 MCU 的代码区和 RAM 都很小，地址又固定，不可能像 PC 一样随便放。

链接后的产物是什么

常见产物是 ELF。在一些 IDE 里也会看到 AXF 这样的名字，本质上还是带有调试和段信息的可执行镜像。

这个文件通常包含：

  • 机器码
  • 各段地址信息
  • 符号表
  • 调试信息

它非常适合调试器使用，但并不是最直接的烧录格式。

四、HEX 和 BIN 到底有什么区别

这一段几乎是面试常客。

1. BIN 是最原始的二进制镜像

BIN 文件里通常只有最纯粹的数据内容，本身不附带地址信息。

所以如果你拿到一个 BIN 文件，烧录工具还必须知道：

  • 这份数据该从哪个起始地址写入

否则它只是一串裸数据。

2. HEX 是带地址和校验信息的文本格式

HEX 常见的是 Intel HEX 格式。它虽然也是用来表示机器码，但里面除了数据外，还会带上：

  • 目标地址
  • 记录类型
  • 校验信息

它本质上是文本格式，所以可读性比 BIN 强得多。

3. 两者怎么选

可以这样简单记：

  • BIN：体积小，适合做升级包、OTA 包
  • HEX：自带地址，适合通用烧录和人工查看

如果是通过串口、网络或文件系统去搬运固件，很多时候大家会更偏向 BIN，因为它更纯、更小。

五、烧录流程到底发生了什么

很多人把“下载程序”想成一个 IDE 按钮动作，但底层其实是 PC、下载器、调试接口、芯片 Flash 控制器一起配合完成的。

我们可以把烧录流程拆成 5 步。

1. PC 先准备好固件文件

这一步就是前面那整条构建链的结果。最终可能交给烧录工具的是：

  • elf/axf
  • hex
  • bin

烧录工具会从这些文件里提取“该往哪个地址写什么数据”。

2. 通过下载器建立连接

常见方式有：

  • SWD
  • JTAG
  • 串口 Bootloader

如果是 STM32 开发里最常见的 ST-Link，那一般走的就是 SWD。

3. 控制目标芯片进入可编程状态

下载器会和 MCU 建立调试连接，然后：

  • 让内核停下来
  • 接管总线访问
  • 操作 Flash 控制器寄存器

这一步之后，下载器就具备了“代替 CPU 改写 Flash”的能力。

4. 擦除目标 Flash，再写入新数据

这一步和我们平时在程序里写 Flash 的原理一样，只不过执行者从“用户代码”变成了“下载器 + Flash 控制器”。

典型动作包括：

  1. 解锁 Flash
  2. 按页或扇区擦除
  3. 分块写入数据
  4. 轮询完成状态

5. 校验并复位运行

写完之后，烧录工具通常还会做一次校验，确认写进去的数据和原始镜像一致。校验通过后，再触发复位，让芯片从复位向量重新启动。

这样新程序才真正开始跑。

六、把烧录流程和存储器理解连起来

一旦把这些环节串起来，你就会发现很多问题会自然对上：

  • 为什么程序能从 Flash 跑：因为链接时代码已经被安排进代码区，复位后 CPU 直接去那块地址取指
  • 为什么烧录必须先擦再写：因为 Flash 的物理特性决定了写入和擦除机制不同
  • 为什么 BIN 适合 OTA：因为它更接近纯净固件镜像，搬运成本更低
  • 为什么链接脚本重要：因为它决定了代码和数据最终到底落在哪

这也是嵌入式里非常典型的一种“从代码到硬件”的理解链。

七、一个面试里比较稳的回答顺序

如果面试官问“hex 和 bin 的区别，或者烧录流程是怎样的”，我觉得可以按这个顺序来讲：

  1. 先讲源代码会经过预处理、编译、汇编、链接
  2. 再讲链接后生成 ELF/AXF
  3. 再讲 ELF 会被转换成 HEX/BIN
  4. 再区分 HEX 自带地址、BIN 是裸镜像
  5. 最后再讲下载器通过 SWD/JTAG/Bootloader 把数据写进 Flash

这样比一上来就背“HEX 是文本，BIN 是二进制”更完整，也更像真的理解了工具链。

总结

STM32 里的“写代码”并不是写完 main() 就结束了。真正完整的链路应该是：

  • 预处理负责展开和裁剪源码
  • 编译、汇编、链接负责生成可执行镜像
  • HEX/BIN 负责把镜像变成更适合烧录或传输的格式
  • 下载器负责通过调试接口把它写进目标 Flash

如果把这条路走通了，你对很多嵌入式问题的理解都会扎实很多。因为你看到的就不再只是某个 IDE 的按钮，而是一整套从源码走到芯片的实际过程。
